Передать существующую папку Hermes

Hermes не является VPS. Он может работать на подходящем компьютере или сервере. Передаём инструкции и данные, затем проверяем инструменты новой среды. История старого чата и установленная локальная программа вместе с папкой не переносятся.

Сначала отдельная копия

Никогда не зачищайте рабочую папку команды. Сначала создайте отдельную экспортную копию, затем удаляйте историю, локальные пути и секреты только из неё. Из корня материалов недели:

python3 week6/scripts/export_team.py /ПУТЬ/К/РАБОЧЕЙ-КОМАНДЕ

Скрипт создаёт рядом папку <имя>-export-<дата> и ZIP, очищает только копию, запрещает симлинки, удаляет локальное состояние и секретные файлы, заменяет персональные домашние пути, проверяет содержимое и сверяет, что исходные файлы не изменились. Для дополнительных папок с клиентскими материалами добавьте их относительные пути по одному на строку в .ai-team-export-ignore исходного проекта и запустите экспорт снова. Не редактируйте исходник ради передачи.

После экспорта вручную откройте MANIFEST.json, README-PEREDACHA.md, ПРИНЯТЬ-КОМАНДУ.md, безопасный пример входа и ZIP. Типичные рабочие каталоги (dela, vhod, vyhod, originaly, arhiv, dashboard, .board) очищаются в копии. Проверьте дополнительные каталоги и бинарные документы: автоматическая проверка не умеет гарантированно распознать все персональные данные. Не передавайте ZIP, пока эта проверка не закончена.

Что подготовить

Чистый экспорт содержит паспорта ролей, навыки с необходимыми скриптами, контракт переходов, диспетчера, правила проекта, безопасный пример входа и ожидаемые критерии результата. Добавьте перечень зависимостей и имён переменных доступа без значений.

Не передавайте .env, приватные SSH-ключи, токены ботов, browser cookies, пользовательскую папку .hermes, платёжные сведения и реальные клиентские материалы без разрешения. .gitignore не удаляет секрет из уже готового ZIP: проверяется содержимое экспорта.

До передачи: локальная приёмка

Упаковывается только версия, которая уже прошла ручное сквозное дело на текущем компьютере. Зафиксируйте вход, выход, проверку и запись журнала. Перенос не используется как способ отладки ещё не работающей связки.

Первый запуск в уже установленном Hermes

1. Передайте проверенный ZIP Hermes как вложение или укажите его доступный локальный путь. Hermes создаёт отдельную постоянную папку проекта и распаковывает туда ZIP, не накладывая его на чужую команду.

2. Откройте терминал в папке распакованного проекта и запустите hermes. Для нового VPS выполните сначала инструкцию VPS. Внутри ZIP откройте ПРИНЯТЬ-КОМАНДУ.md и ведите АКТ-ПРИЁМКИ.md. Первым делом сверьте файлы, размеры и SHA-256 с MANIFEST.json; несовпадение останавливает приёмку.

3. Затем проверьте чтение канонических файлов. Не ограничивайтесь фразой

«файлы найдены»: попросите назвать точные заголовки и по одному безопасному

правилу из каждого файла. Если Hermes не может открыть хотя бы один обязательный

файл, перенос останавливается до исправления рабочей папки или прав.

До любых действий фактически открой README-PEREDACHA.md, agenty/dispetcher.md,
kontekst/pravila-zapuska.md и kontekst/uchet-nedeli-6.md. Для каждого назови
точный заголовок и процитируй одно короткое правило без секретов. Не отвечай по
памяти и не угадывай отсутствующее. Если файл не читается, остановись и назови
точный путь, который недоступен.

4. После успешной проверки отправьте сообщение ниже.

Ты принимаешь существующую команду. Прочитай правила проекта, карту процесса, agenty/dispetcher.md, паспорта ролей и контракты. Покажи назначение команды и состав одного дела. Сверь инструменты, пути, права, проверку результатов и возможность независимого запуска ролей в этой среде. Не переписывай бизнес-логику. Предложи только необходимые адаптации и сохрани после согласования. Не запускай расписание, внешние отправки или реальные дела до проверки. Секреты в ответе не показывай и не проси прислать их в чат.

5. Сравните карту: одна роль осталась одной, две/три связаны только по своему процессу. На одно дело назначается один диспетчер. Не оставляйте старое расписание и новое одновременно включёнными.

6. Проверьте расположение проектных навыков: Hermes обнаруживает их в .agents/skills/ или .hermes/skills/ внутри доверенного Git-проекта. Экспортный ZIP не содержит .git; если вашей версии Hermes нужен Git-корень для проектных навыков, инициализируйте Git только в распакованной папке, без remote и push. Если навыки остались в обычной skills/, адаптируйте расположение без правки канонических правил, затем проверьте обнаружение и доверие командой hermes skills trust <путь>. Настройте недостающие подключения безопасным способом. Проверьте доступ к конкретному ресурсу, а не только наличие переменной.

7. Выполните один пробный сквозной запуск на безопасном входе. Проверьте каждый выход и запись в журнале.

8. Сравните с критериями исходной команды. Различия модели допускаются, потеря обязательных полей и проверок нет.

9. Покажите и проверьте короткий ручной вызов команды: куда положить вход, что написать Hermes, где увидеть статус и результат, как остановить. Только после этого настраивайте сообщения и расписание. В акте приёмки зафиксируйте каждый пройденный шаг и конкретные блокеры.

Kanban не нужен для приёмки одной команды с одним диспетчером. Если роли исполняются разными Hermes-профилями и нужно видеть передачу задач, подключите Kanban после ручной приёмки. Доска не заменяет акт и не появляется сама от распаковки ZIP.

Перенести регулярного механика на новое рабочее место

Сначала механик один раз запускается и проверяется в исходной рабочей папке на компьютере владельца. После ручной приёмки команды в Hermes отправьте отдельную команду:

В этом новом рабочем месте настрой отдельный регулярный разбор журнала навыком mehanik недели 6. Сначала покажи точную рабочую папку, доступный журнал, часовой пояс, расписание, модель, стоимость и получателя рекомендаций. Первый запуск выполни вручную. Задание только читает журнал и сохраняет предложения; оно не меняет паспорта, навыки, подключения или расписания команды. После проверки создай задачу приостановленной или сразу поставь на паузу, покажи её ID, способ ручного запуска, логи, паузу и возобновление. Включай только после моего подтверждения.

Не копируйте расписание с компьютера вслепую. На новом месте другие абсолютный workdir, секреты, модель, инструменты и способ доставки. После переноса выключите старую задачу или явно оставьте только одну активную.

Как инструкции попадут в контекст

Hermes читает проектные файлы по правилам приоритета. Наличие .hermes.md может изменить то, какой файл будет загружен. Не создавайте независимые копии правил в каждом формате: адаптер явно ссылается на канонические документы, затем проверяем чтение реальным запуском.

Обычный Markdown в agenty/ сам по себе не создаёт отдельный процесс. Диспетчер должен использовать доступный механизм делегирования. Если исполнение одной моделью в одном контексте, это нужно явно назвать и не выдавать за независимую проверку.

В CLI рабочая папка берётся из места запуска. Для gateway настройте terminal.cwd. Для каждой cron-задачи укажите абсолютный --workdir: без него проектные инструкции могут не загрузиться. Учебная установка использует один профиль default; существующие профили участника не переключать и не объединять молча.

Когда перенос пока не завершён

  • Навык требует приложения, которого нет на сервере.
  • Проверяющий не может прочитать исходник.
  • Изображения, browser/MCP или API доступны только на старом компьютере.
  • Согласование ожидается в чате, который не подключён.
  • Есть результат, но нет проверки и записи правильной попытки.
  • Папка скопирована, но реальный запуск ещё не выполнялся.
  • Исходная рабочая папка была очищена или перезаписана вместо создания отдельного экспорта.

В отчёте запишите конкретный блокер. Не переименовывайте его в успешный перенос.
