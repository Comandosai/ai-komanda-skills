# Учёт недели 6, версия 1

Новый реестр `dashboard/week6.json`. Он не заменяет `dashboard/config.json` недели 5.
Новый журнал `zhurnal-week6.md`, шесть колонок:
`когда | дело | шаг | кто | исход | примечание`.
Семь исходов: `начал`, `готово`, `отказ: данные`, `отказ: инструмент`, `принято`,
`поправил`, `отклонил`. В примечании `run=<id>;` и наблюдаемый факт. Пояснения
в правилах проекта, в журнале шапка и таблица. Только дописывание событий.

Отдельный журнал исключает попадание неизвестных W6-попыток в старый счётчик.
Диспетчер согласует последовательную запись, роли передают только свои события.
Не добавляй строк за исполнителя, который не запускался. Документированный исход
«нет подходящего сообщения» может быть корректным выходом фильтра; сохраняй файл
результата и проверку условий, не выдумывай статью. Не меняй старую логику недели 5.

## Реестр

Пустой реестр, не учебное достижение:

```json
{"schema_version":1,"attempts":[]}
```

Каждая запись `attempts` содержит:

| Поле | Тип и значение |
| --- | --- |
| id | Уникальная строка, буквы ASCII, цифры, дефис, подчёркивание |
| case_id | Строка номера дела, тот же безопасный набор символов |
| series_id | Строка серии; новая финальная серия после изменения конфигурации |
| mode | trial, final или safety |
| process_id | Стабильное имя выбранного процесса |
| scope_version | Версия границ процесса |
| config_version | Версия инструкций, стыков и подключений, без секретов |
| input_files | Массив путей неизменных входов относительно корня проекта |
| input_hash | Вычисленная сумма комплекта или null, не выдуманное значение |
| data_kind | real или training |
| trigger | manual, schedule или event; фактический способ старта |
| status | running, waiting, completed, stopped или failed |
| result_files | Массив конечных результатов этой попытки |
| check_files | Массив файлов актуальной проверки этой попытки |
| check_passed | true, false или null; соответствует содержанию проверки |
| accepted | true, false или null; отдельно подтверждённая приёмка владельцем/уполномоченным |
| touches | Число ручных действий внутри участка или null, если неизвестно |
| content_corrections | Число содержательных исправлений или null, если неизвестно |
| checked_by | Кто и каким способом проверил: самопроверка, независимый исполнитель, человек |
| started_at | ISO 8601 с часовым поясом |
| finished_at | ISO 8601 с часовым поясом или null |
| reason | Объяснение остановки, ожидания или ограничения; строка |
| event_id | Стабильный ключ входного события/задания либо null; до автоматических внешних действий обязателен |
| approval_files | Массив относительных путей решений по версиям; [] если согласований нет |
| operation_files | Массив относительных путей квитанций/состояний внешних операций; [] если их нет |

Файлы решений и операций хранятся внутри папки попытки. Ключ операции и её фактическое
состояние сохраняются до возможного повторного вызова. Дубликат события в running,
waiting или completed не порождает вторую рабочую попытку. Для safety-теста повтор
фиксируется отдельным наблюдением без нового внешнего эффекта. Правила регистрации
до старта, ожидания, версий и safety находятся в сохранённых правилах запуска.

Внешняя операция содержит event_id, ключ операции, шаг, версию материала, назначение,
статус pending/succeeded/failed/unknown и безопасную квитанцию без секретов.
unknown требует сверки с сервисом, не слепого повтора. Конечная приёмка ссылается
на файл решения владельца, промежуточное «принято» её не заменяет.

Все пути относительные, внутри проекта; запрещены `..`, абсолютные пути и выход
через симлинк. `result_files` и `check_files` непустые для завершения, не пересекаются,
все файлы существуют внутри `dela/<case_id>/<id>/`. Проверка другого дела/попытки
не подходит. Входы не заменять готовыми ответами. Все ожидаемые выходы пакета
перечислены, первая статья не означает готовность пакета из трёх.

Реестр регистрируется до работы, состояние обновляется единственным писателем
атомарной заменой временного файла в той же папке. Сохраняй предыдущую версию.
История событий остаётся в журнале; старые попытки не удаляются. Сам JSON без
блокировки не обеспечивает защиту от гонки, среда должна сериализовать запуски.

## Показатели

«Дошло»: status=completed, check_passed=true, полный действительный комплект
результатов и проверок. Это техническая проверка, не автоматическое одобрение владельцем.
«Принято»: дошло и accepted=true с сохранённым свидетельством принятия.
«Без рук»: дошло и touches=0; null означает неизвестно, не ноль.
«Без содержательных исправлений»: дошло и content_corrections=0, это другая метрика.
Начальная подача входа и старт не касания внутри участка. Согласования, ручные
передачи, подсказки и ручное устранение сбоя внутри участка являются касаниями.

Группируй только по process_id, scope_version, config_version, series_id и mode.
В финальной тройке нужны три разных case_id одной версии, не три перезапуска одного дела.
Не смешивай разные версии и недели. Текстовый отчёт обязан различать неизвестное и ноль.
Автономный запуск: trigger schedule/event подтверждён журналом реального планировщика,
не только полем JSON. Счётчик не доказывает содержательное качество или независимость.

Без инструмента записи выдай реестр и журнал для скачивания, попроси сохранить;
не заявляй автоматический учёт. Без счётчика покажи проверяемую таблицу фактов.
